# Builders are reported by their own rule

**Status:** Accepted

## Context

The setter rule reported each fluent method of a builder, such as one
generated by Lombok's `@Builder`, as a setter. That mixes two problems:
mutation of an object, and a construction API that accepts any subset of
fields. A builder with n optional fields allows 2^n ways to construct an
object; a constructor or factory method is usually enough.

Lombok's `@Builder` is not present in compiled classes, so it cannot identify
a builder.

## Decision

Add a switchable builder rule (`builderMode`, `builderExceptions`) at
Baseline, advisory by default. It reports, once per class:

- every builder type: a class with a `build()` method that returns another
  type and at least one fluent method that returns the class itself;
- every class whose simple name ends in `Builder`.

Both get one message: the class is a builder; prefer a constructor or factory
method. `Builder` names a design pattern, so a class with that name that is
not a builder is a naming defect and is reported too.

The setter rule skips builder types. A class that only matches by name keeps
its setter findings, because it is not a builder and its setters mutate it.

## Considered options

- Keep builder methods in the setter rule. Rejected: the message "is a setter"
  names the wrong problem and reports one finding per field.
- Different messages for builder types and name-only matches. Rejected as
  unnecessary; both are fixed by a constructor, a factory method, or a rename.

## Consequences

Setter advisories on builder methods are replaced by one builder advisory per
builder. Advisories are never frozen, so violation stores are not affected.
